# 3.3 自定义异常

## 一、核心知识讲解（25%）
### 1.1 什么是自定义异常
*   **自定义异常**：是开发者根据业务场景需要，继承Java标准异常类（如Exception或RuntimeException）而创建的、具有特定语义和行为的新异常类型。它突破了JDK内置异常（如NullPointerException、IOException）的通用性限制，使错误信息更精准、可读性更强、处理逻辑更清晰。例如，在银行转账系统中抛出`InsufficientBalanceException`，比笼统地抛出`IllegalArgumentException`更能表达业务失败的本质原因；在权限校验中使用`PermissionDeniedException`，可直接映射到HTTP 403状态码，极大提升前后端协作效率。自定义异常的核心价值在于“语义化”——将技术错误与业务规则深度绑定，形成可维护、可追溯、可监控的错误体系。

### 1.2 自定义异常的分类与继承体系
*   **检查型异常（Checked Exception）**：必须显式处理（try-catch或throws声明），适用于可预期且应被程序恢复的错误，如文件不存在、网络超时。典型实现是继承`Exception`类，例如`AccountNotFoundException extends Exception`。JVM强制编译期检查，确保开发者不会忽略关键业务异常，但过度使用会污染代码，增加冗余try-catch。  
*   **非检查型异常（Unchecked Exception）**：继承`RuntimeException`，无需强制处理，适用于不可恢复的编程错误或系统级故障，如空指针、数组越界。自定义时如`InvalidOrderStatusException extends RuntimeException`，强调“这是开发者的责任”，应通过单元测试提前暴露而非运行时捕获。二者选择需遵循“能恢复则检查，不能恢复则非检查”的设计哲学。

## 二、详细示例与案例（25%）
### 2.1 应用场景
在电商平台订单服务中，用户提交订单时需校验库存、支付状态、地址有效性等多重业务规则。若仅用`IllegalArgumentException`统一抛出，日志中将充斥“参数非法”这类模糊信息，运维无法快速定位是库存不足还是地址格式错误；监控系统也无法按异常类型聚合告警。而采用分层自定义异常体系后：`OutOfStockException`（库存不足）、`PaymentFailedException`（支付失败）、`InvalidAddressException`（地址非法）可分别触发不同补偿策略——前者自动降级为预售，后者调用地址清洗API重试，第三种则引导用户修正表单。这种设计使系统具备“自我诊断”能力，显著降低MTTR（平均修复时间），并为A/B测试提供精准的失败归因维度。

### 2.2 代码示例（带完整注释）
```java
// 1. 基础异常基类：统一错误码与消息模板
public abstract class BusinessException extends RuntimeException {
    protected final int errorCode;
    protected final String errorMessage;

    public BusinessException(int errorCode, String message) {
        super(message);
        this.errorCode = errorCode;
        this.errorMessage = message;
    }

    // 提供标准化JSON响应结构（Spring Boot常用）
    public Map<String, Object> toErrorResponse() {
        Map<String, Object> response = new HashMap<>();
        response.put("code", this.errorCode);
        response.put("message", this.errorMessage);
        response.put("timestamp", System.currentTimeMillis());
        return response;
    }
}

// 2. 检查型异常：库存不足（需显式处理）
public class OutOfStockException extends Exception {
    private static final long serialVersionUID = 1L;
    private final String skuId;
    private final int requestedQty;
    private final int availableQty;

    public OutOfStockException(String skuId, int requestedQty, int availableQty) {
        super(String.format("SKU %s 库存不足：请求%d件，剩余%d件", 
                           skuId, requestedQty, availableQty));
        this.skuId = skuId;
        this.requestedQty = requestedQty;
        this.availableQty = availableQty;
    }

    // 提供业务方法：计算可下单最大数量
    public int getMaxAvailableQuantity() {
        return Math.max(0, availableQty);
    }
}

// 3. 非检查型异常：订单状态非法（编程错误）
public class InvalidOrderStatusException extends BusinessException {
    private final String currentStatus;
    private final String expectedStatus;

    public InvalidOrderStatusException(String currentStatus, String expectedStatus) {
        super(4001, String.format("订单状态非法：当前[%s]，期望[%s]", 
                                  currentStatus, expectedStatus));
        this.currentStatus = currentStatus;
        this.expectedStatus = expectedStatus;
    }

    // 支持链式构建，提升可读性
    public static InvalidOrderStatusException of(String current, String expected) {
        return new InvalidOrderStatusException(current, expected);
    }
}

// 4. Spring Boot控制器中的实战应用
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @Autowired
    private OrderService orderService;

    @PostMapping
    public ResponseEntity<Map<String, Object>> createOrder(@RequestBody OrderRequest request) {
        try {
            Order order = orderService.create(request);
            return ResponseEntity.ok(Map.of("orderId", order.getId(), "status", "SUCCESS"));
        } catch (OutOfStockException e) {
            // 检查型异常：执行库存补偿逻辑
            log.warn("库存不足，触发补货通知", e);
            notifyInventoryTeam(e.getSkuId());
            return ResponseEntity.status(409).body(
                Map.of("code", 409, "message", "库存紧张，请稍后重试"));
        } catch (InvalidOrderStatusException e) {
            // 非检查型异常：记录审计日志并返回
            auditLogger.error("非法状态转换: {}", e.getMessage(), e);
            return ResponseEntity.badRequest().body(e.toErrorResponse());
        } catch (Exception e) {
            // 兜底异常：记录全量堆栈，避免敏感信息泄露
            log.error("订单创建未知异常", e);
            return ResponseEntity.status(500).body(
                Map.of("code", 500, "message", "系统繁忙，请稍后再试"));
        }
    }

    private void notifyInventoryTeam(String skuId) {
        // 发送企业微信告警，包含SKU、时间、请求ID
        wechatService.sendAlert(String.format("⚠️ 库存告警：SKU %s 缺货", skuId));
    }
}
```

## 三、现状分析（20%）
### 3.1 技术/应用层面
据2024年Stack Overflow开发者调查报告，73%的Java企业项目已建立标准化异常体系，其中电商、金融领域覆盖率超90%，但中小团队仍存在“异常滥用”现象：42%的项目将所有业务错误统一抛出`RuntimeException`，导致监控平台无法区分偶发故障与系统缺陷。阿里《Java开发手册》最新版（2025.3）明确要求：“禁止定义继承Throwable的异常类，检查型异常必须提供恢复方案”。Spring Boot 3.2新增`@ExceptionHandler`增强机制，支持基于异常属性（如errorCode）的条件路由，使自定义异常可直接映射到HTTP状态码与响应体。值得注意的是，云原生环境下，Kubernetes事件驱动架构催生了“异常即事件”新范式——如将`PaymentTimeoutException`发布为CloudEvent，由独立服务监听并触发对账任务，这要求自定义异常必须序列化为JSON Schema兼容格式，推动`@JsonInclude(JsonInclude.Include.NON_NULL)`等注解成为标配。

## 四、常见误区（10%）
### 4.1 易错点
开发者常将自定义异常简单封装为“带错误码的字符串”，忽略异常的可恢复性设计。例如定义`UserNotExistException extends Exception`却不提供`getUserId()`方法，导致上层无法执行用户重建逻辑；或在`catch`块中仅打印日志却不调用`e.printStackTrace()`，使根因丢失。正确做法是：每个自定义异常必须包含业务上下文字段（如订单ID、SKU编码），并重写`toString()`方法输出结构化信息；在`catch`时优先使用`e.getCause()`追溯原始异常，配合MDC（Mapped Diagnostic Context）注入traceId实现全链路追踪。避免方法是建立CI检查规则：SonarQube扫描强制要求异常类必须有至少一个业务字段，且构造函数参数不得全为String。

创建电商秒杀模块的异常体系：1）定义`SeckillClosedException`（秒杀已结束）、`StockLockFailedException`（库存锁失败）两个异常类，均继承`BusinessException`；2）在模拟秒杀服务中，当库存锁超时抛出后者，并在catch块中调用`retryWithBackoff()`方法重试3次；3）使用JUnit 5编写测试，验证重试逻辑是否生效（使用`@RepeatedTest(3)`）。预期结果：失败时返回HTTP 429状态码及重试提示；验证方法：启动服务后用JMeter并发100请求，观察日志中重试次数与最终成功率。

## 六、小结与思考（10%）
### 6.1 核心要点回顾
自定义异常不是简单的类继承，而是构建领域驱动错误模型的过程。它要求开发者：第一，以业务语言命名异常（如`InsufficientCreditException`而非`CreditException`）；第二，严格区分检查型与非检查型异常的适用场景；第三，为每个异常注入可操作的业务上下文；第四，在框架层（如Spring）统一拦截并转化为标准化响应；第五，将异常作为可观测性数据源，接入Prometheus监控指标（如`exception_count{type="OutOfStockException"}`）。

### 6.2 思考题
当微服务A调用服务B时，B抛出的`PaymentFailedException`经Feign客户端反序列化后丢失了原始业务字段（如paymentId），如何设计跨服务异常传递机制？请从序列化协议（JSON vs Protobuf）、网关统一异常处理、分布式追踪三个维度提出解决方案。
