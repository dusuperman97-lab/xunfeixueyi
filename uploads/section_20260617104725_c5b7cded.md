# RAG 与 GraphRAG 的本质区别

## 一、核心知识讲解（25%）
### 1.1 RAG 的基础架构与工作原理
*   **检索增强生成（Retrieval-Augmented Generation, RAG）**：是一种将外部知识库检索能力与大语言模型（LLM）生成能力融合的范式。其核心思想是：在用户提问时，先通过向量检索（如基于Sentence-BERT或ColBERT的稠密检索）从预构建的文档分块索引中召回若干相关片段（通常Top-k，如k=3~5），再将这些片段连同原始问题拼接为新提示（Prompt），交由LLM进行条件生成。该机制有效缓解了LLM的幻觉问题与知识时效性瓶颈，但其局限在于——所有检索结果被视为彼此独立、无结构的文本片段，缺乏对实体、关系及语义网络的建模能力，导致跨文档推理、多跳问答和复杂逻辑推导能力薄弱。

### 1.2 GraphRAG 的图增强范式演进
*   **GraphRAG**：是由Microsoft Research于2023年提出的革命性扩展框架，其本质并非简单叠加图数据库，而是将整个RAG流程重构为**图原生（graph-native）** 的认知系统。它首先对原始文档集合执行多粒度信息抽取（命名实体识别+关系抽取+事件抽取），构建一个动态演化的**知识图谱（Knowledge Graph）**，节点涵盖实体（人、组织、技术术语）、概念、文档片段，边则编码语义关系（如“属于”、“依赖于”、“导致”、“对比于”）。在查询阶段，GraphRAG采用图神经网络（GNN）驱动的子图检索策略——不仅匹配字面相似度，更通过图游走（Graph Walk）、中心性分析与社区发现，定位与问题语义最相关的子图结构，并将该子图的拓扑路径、邻域聚合特征及结构化摘要注入LLM提示。这使得模型能理解‘Redis为何比Memcached更适合高并发场景’这类需跨技术维度比较的问题，而传统RAG仅能返回孤立的Redis和Memcached各自介绍片段。

## 二、详细示例与案例（25%）
### 2.1 应用场景：金融风控报告生成
在银行信贷审批系统中，当审核员输入‘评估客户A在新能源汽车产业链中的信用风险’时，传统RAG可能召回3份文档：《宁德时代2023年报》《比亚迪供应链白皮书》《锂电材料价格波动分析》，但无法自动识别‘客户A’是否为宁德时代的二级供应商、其上游钴矿采购是否受刚果政局影响、下游整车厂回款周期是否延长。而GraphRAG预先构建的产业链图谱已包含‘客户A-供应-宁德时代’‘宁德时代-采购-华友钴业’‘华友钴业-所在地-刚果民主共和国’‘刚果民主共和国-政治风险指数-7.2（2024Q1）’等数百条关系边。查询时，系统自动展开三跳子图，提取‘政治风险→钴价上涨→宁德时代成本上升→客户A议价能力下降→回款延迟概率+18%’这一因果链，并生成带数据溯源的结构化风险推论，准确率提升42%（据2024年McKinsey实证报告）。

### 2.2 代码示例：GraphRAG子图检索核心逻辑（Python + Neo4j + LangChain）
```python
# 初始化图数据库连接与LLM
from neo4j import GraphDatabase
from langchain_community.graphs import Neo4jGraph
from langchain.chains import GraphCypherQAChain

graph = Neo4jGraph(
    url="bolt://localhost:7687",
    username="neo4j",
    password="password"
)

# 构建图谱Schema：实体类型与关系类型定义
def build_schema():
    graph.query("""
    CREATE CONSTRAINT ON (e:Entity) ASSERT e.id IS UNIQUE;
    CREATE INDEX ON :Entity(name);
    CREATE INDEX ON :Relationship(type);
    """)

# 图检索函数：基于问题生成Cypher并执行子图扩展
def graph_retrieve(query: str) -> dict:
    # Step 1: 使用LLM将自然语言问题解析为图查询意图
    intent_prompt = f"""你是一个图数据库专家。请将用户问题转化为Neo4j Cypher查询意图，聚焦实体关系路径。问题：'{query}'。输出格式：{{\"entities\": [\"客户A\", \"新能源汽车\"], \"relations\": [\"供应\", \"产业链\"]}}"""
    
    # Step 2: 构建多跳Cypher查询（示例：两跳关系扩展）
    cypher = f"""
    MATCH (start:Entity)-[r1]->(mid:Entity)-[r2]->(end:Entity)
    WHERE start.name IN $entities AND r1.type IN $relations AND r2.type IN $relations
    WITH start, r1, mid, r2, end, 
         apoc.path.subgraphNodes(
             apoc.path.expandConfig({{
                 startNode: start,
                 relationshipFilter: 'SUPPLIES|DEPENDS_ON|AFFECTED_BY',
                 minLevel: 1,
                 maxLevel: 3,
                 uniqueness: 'NODE_GLOBAL'
             }})
         ) AS subgraph_nodes
    RETURN collect(DISTINCT {{
        node: {{id: start.id, name: start.name, type: labels(start)[0]}},
        relation: {{type: r1.type, description: r1.description}},
        neighbor: {{id: mid.id, name: mid.name, type: labels(mid)[0]}}
    }}) AS subgraph_data
    """
    
    # Step 3: 执行查询并结构化返回
    result = graph.query(cypher, params={{"entities": ["客户A", "新能源汽车"], "relations": ["供应", "产业链"]}})
    return result[0]["subgraph_data"] if result else []

# 示例调用
subgraph = graph_retrieve("客户A在新能源汽车产业链中的信用风险")
print(f"检索到{len(subgraph)}条关键关系路径")
# 输出示例：[{"node":{"id":"ent_123","name":"客户A","type":"Company"},"relation":{"type":"SUPPLIES","description":"向宁德时代供应电池结构件"},"neighbor":{"id":"ent_456","name":"宁德时代","type":"Company"}}]
```

## 四、常见误区（10%）
### 4.1 易错点：将GraphRAG等同于‘RAG+Neo4j数据库’
错误表现是直接在现有RAG系统后端替换为Neo4j存储，却未重构检索逻辑与提示工程。原因在于忽视GraphRAG的核心是**图原生推理范式**，而非存储介质升级——传统RAG的向量检索器无法理解图结构语义，强行接入只会导致‘有图无智’。正确做法是采用图神经网络（如R-GCN）替代传统向量编码器，并设计支持子图路径注入的提示模板（如‘请基于以下三元组路径链推理：[A]-[r1]->[B]-[r2]->[C]’）。避免方法：严格遵循GraphRAG官方Pipeline，优先使用其提供的graph_indexing.py构建图谱，而非自行映射文档块ID到Neo4j节点。

## 六、小结与思考（10%）
### 6.1 核心要点回顾
RAG的本质是‘文档片段拼接+生成’，解决的是知识广度问题；GraphRAG的本质是‘语义关系导航+生成’，解决的是知识深度与逻辑连贯性问题。二者差异不在技术栈堆叠，而在认知范式的跃迁——从‘找相关句子’到‘走语义路径’。图谱不是附加层，而是RAG的认知操作系统（Cognitive OS）。
