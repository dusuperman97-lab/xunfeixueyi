# 索引阶段：文档解析→图构建→社区发现

## 一、核心知识讲解
### 1.1 文档解析：从非结构化文本到语义单元
*   **文本分块（Text Chunking）**：这是索引流程的起点，其本质是将原始PDF、Markdown或网页等非结构化文档切分为语义连贯、大小适中的文本单元（TextUnit）。微软GraphRAG默认采用基于token计数的滑动窗口策略（如300 token），但更推荐使用语义感知分块——例如按段落、标题层级或自然语言标点（句号、换行符）进行切分，以避免割裂实体关系。关键在于平衡：过小的块（<100 token）会导致实体上下文缺失，无法识别“苹果公司CEO蒂姆·库克宣布新iPhone发布”中的“苹果公司”与“蒂姆·库克”的归属关系；过大的块（>1200 token）则会引入噪声，使LLM在后续提取时混淆无关信息。实践中，应结合文档类型动态调整：技术文档宜用代码块+注释为单位，法律文书宜以条款为单位，而新闻稿则以事件主体为单位。该步骤输出的每个TextUnit都携带元数据（source_document_id、position_in_doc），为后续溯源提供关键锚点。

### 1.2 图构建：从文本单元到知识图谱基元
*   **实体-关系联合抽取（Joint Entity-Relation Extraction）**：此步骤利用大语言模型（如GPT-4o-mini）对每个TextUnit进行深度语义分析，同步识别出三类核心图谱基元：**实体（Entity）**（指现实世界中可独立存在的对象，如人、组织、地点、概念，需具备唯一标识name、类型type及描述description）、**关系（Relationship）**（连接两个实体的语义纽带，如“创始人”、“位于”、“属于”，需明确source、target及描述description）和**主张（Claim）**（带有可信度评估的陈述性事实，如“微软于2023年收购GitHub”，含status字段）。与传统NER+RE流水线不同，GraphRAG采用端到端提示工程，要求LLM一次性输出结构化JSON，显著降低误差累积。例如，对句子“特斯拉CEO埃隆·马斯克于2023年宣布Cybertruck量产”，模型需同时生成实体[{'name': '特斯拉', 'type': '公司'}, {'name': '埃隆·马斯克', 'type': '人物'}, {'name': 'Cybertruck', 'type': '产品'}]及关系[{'source': '埃隆·马斯克', 'target': '特斯拉', 'description': '担任CEO'}, {'source': '特斯拉', 'target': 'Cybertruck', 'description': '研发并量产'}]。所有TextUnit的子图最终被合并：同名同类型的实体通过合并description数组实现去重与信息增强，相同source-target的关系亦作聚合，形成初始知识图谱骨架。

### 1.3 社区发现：从扁平图谱到层次化语义聚簇
*   **层次Leiden算法（Hierarchical Leiden Algorithm）**：这是GraphRAG区别于传统图RAG的核心创新。它并非简单聚类，而是对实体节点构成的加权无向图（边权重由关系置信度或共现频率决定）执行递归社区检测，生成一棵“社区树”。算法从全图开始，反复应用Leiden优化（最大化模块度Modularity），直至每个社区内节点密度高于阈值（如min_community_size=15）。结果是一个多粒度结构：根节点代表整个知识库的全局主题（如“人工智能技术生态”），中间层对应子领域（如“大模型训练框架”、“RAG架构演进”），叶节点则是高度聚焦的语义簇（如“LangChain与LlamaIndex对比”、“GraphRAG社区摘要生成机制”）。每个社区节点均关联一个唯一的community_id，并通过IN_COMMUNITY关系链接其成员实体。这一结构直接支撑了后续的“映射-归约”式查询——系统可先在粗粒度社区快速定位相关主题，再下沉至细粒度社区获取精准细节，彻底解决传统RAG因文本片段孤立而导致的跨文档推理断裂问题。

## 二、详细示例与案例
### 2.1 应用场景：企业级知识中枢构建
在某跨国金融科技集团的内部知识管理项目中，GraphRAG索引阶段处理了超过50万份文档，涵盖监管政策、产品白皮书、客户案例与内部会议纪要。传统RAG仅能回答“《巴塞尔协议III》对资本充足率的要求是什么？”这类单点问题，而GraphRAG通过索引阶段的社区发现，自动构建出“全球金融监管合规”这一顶层社区，并在其下衍生出“欧盟GDPR”、“美国SEC新规”、“亚太地区反洗钱标准”等子社区。当高管提出“对比分析主要经济体2024年AI金融监管趋势”这一QFS（Query-Focused Summarization）型全局问题时，系统无需遍历全部文档，而是直接调用各子社区的LLM生成摘要，再汇总提炼出结构化报告，将原本需数周的人工研报工作压缩至分钟级。该案例证明，索引阶段的质量直接决定了GraphRAG能否胜任复杂决策支持场景。

### 2.2 代码示例：本地化GraphRAG索引流程（Python）
```python
# 1. 初始化配置（基于graphrag官方CLI）
import subprocess
import json

# 创建自适应中文提示模板（关键预处理）
subprocess.run([
    "python", "-m", "graphrag.prompt_tune",
    "--language", "Chinese",
    "--root", "./finance_knowledge_base"
], check=True)

# 2. 执行索引流程（核心命令）
index_cmd = [
    "python", "-m", "graphrag.index",
    "--root", "./finance_knowledge_base",
    "--config", "./finance_knowledge_base/graphrag_config.yaml"
]
result = subprocess.run(index_cmd, capture_output=True, text=True)
if result.returncode != 0:
    raise RuntimeError(f"索引失败: {result.stderr}")

# 3. 解析输出的Parquet文件（验证社区结构）
import pandas as pd

# 加载社区报告（关键产物）
community_reports = pd.read_parquet(
    "./finance_knowledge_base/output/20240413120000/communities.parquet"
)
print(f"共生成{len(community_reports)}个社区")
print("顶级社区示例:")
print(community_reports[community_reports['level'] == 0][['title', 'summary']].head(3))

# 4. 加载实体-关系图（可视化准备）
entities = pd.read_parquet(
    "./finance_knowledge_base/output/20240413120000/entities.parquet"
)
relationships = pd.read_parquet(
    "./finance_knowledge_base/output/20240413120000/relationships.parquet"
)

# 构建NetworkX图并计算中心性（验证社区质量）
import networkx as nx
import matplotlib.pyplot as plt

G = nx.Graph()
# 添加实体节点
for _, row in entities.iterrows():
    G.add_node(row['id'], name=row['title'], type=row['type'])
# 添加关系边（带权重）
for _, row in relationships.iterrows():
    if row['weight'] > 0.7: # 过滤低置信度关系
        G.add_edge(row['source'], row['target'], weight=row['weight'])

# 计算PageRank中心性，识别关键实体
pagerank = nx.pagerank(G, weight='weight')
print("Top 5 关键实体（PageRank）:")
for entity_id, score in sorted(pagerank.items(), key=lambda x: x[1], reverse=True)[:5]:
    entity_info = entities[entities['id'] == entity_id]
    if not entity_info.empty:
        print(f"  - {entity_info.iloc[0]['title']} ({entity_info.iloc[0]['type']}): {score:.4f}")
```

## 四、常见误区
### 4.1 易错点：盲目追求大模型能力而忽视分块策略
错误表现是直接将整篇PDF丢给LLM做“端到端解析”，导致实体关系提取准确率低于40%。根本原因在于LLM的上下文窗口限制（即使128K token）无法承载长文档的全局语义，且缺乏结构化约束易产生幻觉。正确做法是实施“三级分块策略”：一级按文档逻辑结构（章节/小节）粗分；二级在每块内按语义单元（如一个技术方案描述）细分；三级对关键段落进行词元级对齐（确保实体名称不被截断）。避免方法包括：使用`langchain.text_splitter.RecursiveCharacterTextSplitter`配置`chunk_size=500`与`chunk_overlap=50`，并添加`separators=["\n\n", "\n", " "]`优先按段落分割；对分块结果进行人工抽检，确保每个块包含完整主谓宾结构。

## 六、小结与思考
### 6.1 核心要点回顾
索引阶段绝非简单的数据预处理，而是GraphRAG智能性的源头。它通过**文档解析**建立语义单元锚点，通过**图构建**将离散文本升维为结构化知识网络，再通过**社区发现**赋予网络层次化语义理解能力。这三个环节环环相扣：分块质量决定实体抽取上限，图构建精度影响社区划分合理性，而Leiden算法的参数（如resolution、max_iterations）则直接调控社区粒度，需根据业务需求精细调优。掌握此阶段，意味着掌握了将海量信息转化为可推理、可导航、可演化的知识资产的核心能力。
